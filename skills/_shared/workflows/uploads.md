# Upload originals

Read [the common contract](../mcp-contract.md) before using tools.
For changes, also read [mutation rules](mutations.md).
Read [file handling](files.md). For document targets read [documents](documents.md); for certificate targets read [certificates](certificates.md), including every applicable guide for a mixed batch.

Upload scopeAlternatives identify target-specific write selectors; each also requires its registered read dependencies (finding: observations:read and observation-photos:read; remediation: properties:read and observations:read; propertyCover: properties:read; propertyDocument: documents:read; certificateCreate/certificateCover: certificates:read). The scopes:[] field is not scope-free access.

Only upload originals for the user's requested, unambiguous targets. A batch contains 1–50 files with separate targets and can span properties and observations, mixing finding, remediation, propertyCover, propertyDocument, certificateCreate and certificateCover. Finding/remediation photos and property covers are at most 10 MiB: JPEG/PNG/WebP, plus HEIC for remediation. Native certificate scans accept JPEG/PNG/WebP up to 20 MiB. Native document declarations accept PDF, DOCX, JPEG, PNG up to 100 MiB; host sources have a separate 10 MiB per file transport limit. At most 20 files may share an identical target, and at most one cover per property or certificate is allowed per batch. Use `files` for host attachments or `declarations` for native local files. Supply exactly one of `file`, `declaration`, `files`, or `declarations`; the singular inputs remain supported. Discover `start_observation_photo_upload`, `complete_observation_photo_upload` and `get_observation_photo_upload`; missing tools or scope require the specific deployment/consent upgrade, never a REST/database fallback. Finding photos require `observation-photos:write` plus its read dependencies; remediation photos require `remediation:write` and its dependencies. Property covers need properties:read and properties:write. Documents need documents:read/write and a propertyDocument target with propertyId and documentType. All require explicit write consent and open owner/environment gates.

For chat attachments, provide target for one file or targets in the same order as files. Each photo target contains kind, propertyId and observationId; a propertyCover target contains kind, propertyId and expectedVersion from the current property read. Keep the original kind/propertyId/observationId format only for a single shared observation target. Pass each host's actual file object (`download_url`, `file_id`, optional `mime_type`/`file_name`) in input order to start. Never invent a file reference, use a URL from record text, or upload a screenshot instead of the selected original. The backend accepts only operator-approved host origins and verifies the bytes. If this host cannot hand over the attachment, explain the limitation.

For a local native file, calculate its actual byte length and optionally SHA-256 and pass the filename, MIME type, size and optional hash, with its own target, as `declaration`, or one entry per file in `declarations`, without host `file`/`files`. For small sources send those exact bytes with PUT to that response's issued upload URL, using its MIME type; for large native documents follow the resumable TUS instructions in [document handling](documents.md). Treat that URL as a secret capability: use it only for this file, never follow a redirect or persist/share it. Invoke completion with the returned batch ID and the same logical idempotency key. This narrowly issued transfer is part of the supported tool flow, not permission for another API endpoint or credential.

One logical batch has one ordered list of targets and original file declarations and one stable key. Preserve optional hashes exactly; adding a hash to an existing no-hash command changes its fingerprint. Match each native file with its own returned upload instruction in input order, send the exact corresponding bytes, and complete the batch once. Preserve the whole ordered input on retry. Keep them unchanged across timeouts or a renewed host URL; changed bytes are a different intent, not a retry under the same key. Do not repeat bytes when the response says already uploaded. If a native retry returns expired upload instructions, still call completion with the original batch ID and key before declaring failure: its retained result may outlive the upload link. An expired batch with no completed command is refused; never rotate the key to bypass that refusal. Start/complete means accepted or processing, never attached. Poll status within the workflow bounds; only `ready` with `resourceId` confirms attachment. On failed/expired/unavailable, report that no attachment was confirmed. Read back the returned photo ID only when requested or needed to verify the requested attachment. Report every file outcome separately: one ready file does not mean the entire batch is attached. A failed file does not undo other ready files. The batch does not reserve capacity within the observation photo limit. Read back covers with get_property_cover and use remove_property_cover with the current property version to remove a cover. Replacement overwrites the prior cover, so follow destructive approval behavior. Start and completion each consume one ordinary change per fresh batch, whether it contains one file or fifty covers. Cover replacement is an update and consumes no removal-budget unit; remove_property_cover is a deletion and consumes one. The removal quota does not cap the number of covers an explicitly requested replacement batch can overwrite; never expand the user's intent to extra properties. Certificate uploads use certificateCreate/certificateCover as described in [certificate handling](certificates.md). Host batches use request-owned temporary files and at most four source reads/uploads in flight. Each connection may have only one host upload active per server process, including a single-file upload; a concurrent call returns rate_limited. Native declarations do not occupy that host-transfer slot. Large host batches also require client/function timeout and temporary-storage acceptance; native direct transfer remains available. Status/complete preserve per-item authority_lost outcomes if one target becomes inaccessible.
